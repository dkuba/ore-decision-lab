# Ore Decision Lab — План реализации

**Стиль:** Scientific Light. **Хостинг:** GitHub Pages (`/ore-decision-lab/`). **Интерактивное ядро:** TypeScript в браузере, без backend и секретов. **Статус на 23.11.2026:** код v0.1 размещён в публичном GitHub, P0 и P1 завершены, P2 проверен локально и в CI (продакшн URL ещё требуется проверить). Оператор и контакт указаны; P3 ждёт настройки GitHub Pages Source: GitHub Actions и успешного деплоя. Все сведения о руде синтетические; это лаборатория демонстрации логики, а не инженерный совет.

## Что должен доказать PoT

1. **Причинная инженерная логика:** наблюдённые признаки руды запускают *гипотезы исследований*, а не выдуманные проценты извлечения.
2. **Воспроизводимость:** извлечение каждой стадии рассчитывается по независимо измеренным синтетическим продуктам, с QA-невязкой и исходным протоколом.
3. **Границы знания:** missing testwork, отсутствие минералогии, ограничения площадки, выход за диапазон и конкурирующая неверифицированная модель не выдаются за одобренную технологию.
4. **Контрфактическая проверка:** на руде C пользователь меняет содержание Au и модель потерь; система объясняет, почему одна модель даёт границу (~1,29 г/т), а вторая — нет, и фиксирует конфликт второй с крайними испытанными точками.

## P1 — структура экрана

- **Верх:** ясное позиционирование и ограничения «fully synthetic / not engineering approval».
- **Слева:** выбор A–D; редактирование содержаний *только у C*; отдельные переключатели `mineralogy_available`, `testwork_available`, `heap_site_feasible`.
- **Центр:** сравнительный график C с зоной неразличимости и линиями разных моделей; таблица допустимых и недопустимых маршрутов.
- **Справа:** объяснение правила и статуса, измеренная доля Au, потоки, финансовый показатель screening-only; программа необходимых испытаний.
- **Низ/панель:** прямой просмотр лабораторного протокола, formula trace, source id и 12 публикаций с границами применимости.
- **Два уровня подробности:** руководитель (ключевые развилки) / инженер (балансы, имена тестов, QA).

## Контракт данных и решения

- Не менять значения `public/data/*` без новой версии исходных фикстур; это **синтетические измерения**, а не реальные данные.
- Отделить `source_kind` (SYNTHETIC_LAB / LITERATURE_MECHANISM / ASSUMED_COST / USER_WHAT_IF) от evidence status (supported / missing / out_of_scope / hypothesis).
- Правила возвращают **кандидаты для исследований**, не промышленно готовые рекомендации.
- Числовой результат разрешён лишь при наличии подтверждённого учебного опыта, правильных stage mapping, QA и пригодном domain scope.
- Поток `FLOT → POX/BIOX` считается произведением; поток `GRAV → tails CIL` — сумма извлечённого из концентрата и остатка. Balance QA из измеренных продуктов, а не из навязанного остатка.
- C `constant_residue` — гипотеза, противоречащая крайним узлам; у неё **нет confirmed winner** даже при показе условного лидера.
- На ширине < 760px экран перестраивается в одну колонку. Нет обязательной авторизации, загрузки чужих файлов и внешних вызовов при расчёте.
- Ссылка состояния содержит только `ore`, `grade`, `model`, `mineralogy`, `testwork`, `heap_site`; никаких персональных данных.

## Порядок интеграции с GitHub и приёмки

1. Разместить весь код в `dkuba/ore-decision-lab`, в отдельной ветке и через Pull Request. CI на `pull_request` выполняет `npm run test`.
2. Слить Pull Request в `main` только после успешного CI; этот шаг **не** публикует сайт автоматически, пока `ODL_PUBLISH_ENABLED` не установлен.
3. Владельцу включить Settings → Pages → Source: GitHub Actions.
4. Имя оператора и контакт уже записаны в `public/site_config.json`; переменная `ODL_PUBLISH_ENABLED` более не используется. Публикация срабатывает автоматически из `main` после `verify`.
5. После публикации проверить `/ore-decision-lab/`, query-параметры, копирование URL, 12 протоколов, формулы и все четыре руды на десктопе и телефоне.
6. Первым 5–10 отраслевым пользователям показать открытый PoT; собирать качественные замечания и запросы на техническое обследование, а не только просмотры.

## Проверки перед выпуском

1. Unit/reference parity для всех 14 опубликованных контрольных векторов и A–D базовых профилей.
2. Негативные векторы: скрытое testwork, отсутствующая минералогия, лабораторный QA, ложная проницаемость, вне диапазона C, `constant_residue` не утверждает лидера.
3. Статический бандл не содержит `regression/expected.json`, Python-генератора, серверных ключей или приватных данных.
4. График и таблица всегда получают результат **из одного вычисления**; UI не имеет `if (ore === A) leader = ...`.
5. На публикации указан оператор проекта Кубарев Дмитрий Владимирович, `dkubarev@ya.ru`; проверка HTTPS-сайта ещё не завершена.

## Осознанные ограничения

Первая итерация использует TypeScript + browser DOM и CSS без тяжёлого фреймворка: меньше зависимостей, проще инспектировать расчёт и непосредственно публиковать в GitHub Pages. В случае расширения до масштабируемого рабочего приложения UI можно перенести на React без изменения контрактов ядра.

Рассчитанные стоимостные показатели — условные USD/т и не являются NPV, CAPEX/OPEX или проектным ТЭО. Перенос эмпирических коэффициентов на новую руду без квалификации запрещён.
